name: project-setup
description: Connect an existing Minecraft Java mod to craft-foundry with explicit Gradle targets, artifacts and human-approved validation ownership.
---

Read the installed package's `docs/configuration.md` and `docs/development.md`. Before implementation, use `templates/validation/README.md` to list AI checks, human checks and untested scope; obtain human confirmation. Select requirements from supported sides/features and the actual change. AI focuses on feature functionality, build/logic and essential affected persistence; detailed GUI interaction, feel and balance default to humans. Human-pending is not failure or a request for exhaustive automation.

Use [Minecraft development basics](../minecraft-development-basics/SKILL.md) when choosing native inventory menus/screens, sides, registration, resources and persistence. Check each selected target's resolved sources/mappings rather than generalizing class names across versions.

Map the project's existing Gradle tasks and explicit distribution/runtime JARs in `harness.config.json` and its artifact manifest. Keep Minecraft, loader, mappings and plugin/build dependency versions authoritative and fixed in Gradle. Runtime metadata normally permits the development loader/Fabric API version and newer; Minecraft compatibility is separate, and known exclusions require evidence. A permissive metadata range does not prove every version tested. NeoForge's metadata `loaderVersion` is the language-loader range, distinct from the `neoforge` dependency.

Keep Java homes, tool/backend paths and EULA acceptance in ignored `harness.local.json`. Pin downloaded tools by version/HTTPS URL/SHA-256 in `harness.lock.json`. Distinguish Gradle, compile and game Java. The four fixtures use Forge 1.20.1 at 17/17/17, Fabric 1.20.1 at 21/17/17 and both 1.21.1 targets at 21/21/21; other projects must inspect their own resolved requirements.

Run `mch doctor --json` and `mch inspect --target <id> --json` for the approved setup. Missing prerequisites are environment diagnostics, not a Mod regression. Use `templates/existing-project` as a starting example, then map agreed automated requirements to `requiredSuites`. Keep unimplemented agreed required suites explicitly unsupported; do not drop requirements to obtain a release pass. Record manual checks separately in the plan/result document. The full `templates/multiloader` fixture matrix is not every consumer's mandatory test plan.

For changed persistent state, agree representative item/data integrity checks; use `docs/persistence.md` and `server-persistence` when clean save/restart/restore proof is needed. Unrelated persistent systems need not be retested for every edit. For affected acquisition, optionally use `templates/acquisition/README.md` and the repository-only `docs/survival.md` with exact Forge/Fabric 1.20.1 or NeoForge/Fabric 1.21.1 adapters. A required current-build Atlas check needs fresh `captureRuntime` identity and complete evidence; an old dump or viewer entry is not execution proof. Unknown hooks and incomplete/finite coverage stay explicit. The npm package does not ship the Atlas runner; its absence is not a blanket blocker for ordinary setup.

Treat Mod/config/datapack additions, updates and removals as ordinary operation; optional integrations degrade locally. Protect items/data without freezing entire files/environments. Prefer native mechanisms; agree prerelease/new-save breaks instead of inventing speculative migrations. Consult the human before restrictive startup refusals, player interaction restrictions or compatibility narrowing. Select relevant Modpack combinations and provide actionable diagnostics.

Read `docs/storage.md` before enabling opt-in managed caches/shared assets/cleanup. Inventory with `mch storage --json` and preview with `mch storage --clean --json`; apply only exact authorized targets. Keep historical unmarked data, worlds, settings and evidence. Asset reuse verifies immutable bytes and supplies independent session files; logical sizes do not prove physical savings. For `after-suite`, reserve across restarts, lease each process use, confirm shutdown, durably attach immutable scoped seals, release all leases and close after final use. Preserve `storageEvidence` and use a 0.1.10-or-later reader. Harness evidence/ownership rules do not impose product behavior.

Upgrade consumer Skills with the installer and review `preserved` edits before any replacement. Setup alone authorizes no publication, deployment or consumer customization overwrite.
