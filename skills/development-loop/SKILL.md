Before implementation, list the change, affected targets, AI checks, human checks and out-of-scope/untested behavior, then obtain human confirmation of that division. Use the installed package's `templates/validation/README.md` and `docs/development.md`. A later material scope change needs renewed agreement; do not repeatedly ask for approval of routine steps already covered.

Use [Minecraft development basics](../minecraft-development-basics/SKILL.md) for native inventory menus/screens, logical sides, registration, resources and state. Select a target with `mch targets --json` and inspect resolved sources/mappings using `mch inspect --target <id> --json` before using version-specific APIs.

For code changes, normally build the affected target with `mch build --target <id> --json` and run the agreed affected `mch test --target <id> --suite <id> --json` checks. AI primarily verifies feature functionality, build/logic and essential affected persistence. Detailed GUI interactions, play feel and balance default to human review. Documentation/guidance-only changes need no Minecraft launch. Choose relevant Modpack combinations from changed integrations and known risks, not every combination.

Inspect `mch report --run <run-id> --json` for detected cases, artifact hashes and evidence; an exit code alone is not proof. Report AI outcomes, human-pending checks and untested scope separately. Human-pending is not a failed assertion and must not trigger exhaustive automation. Do not invent human passes, encode pending review as a fake machine result, or relabel an actual failed/unsupported/skipped/zero-detected required check. A passing Run establishes only its declared automated coverage. Before a release, run `mch test --all --profile release --json` for every agreed required automated suite and separately review human release criteria. Do not delete existing requirements merely to obtain a pass.

Pin build dependencies for reproducibility; runtime compatibility metadata normally allows the development loader/Fabric API version and newer, with Minecraft's range separate. Exclude known incompatibilities with evidence. Unknown compatibility is not incompatibility. NeoForge `loaderVersion` describes the language loader, not the `neoforge` dependency. See `docs/development.md` for metadata examples.

Treat Mod/config/datapack additions, updates and removals as normal operation. Optional integrations should degrade locally when absent or unsupported. Prefer simple native mechanisms and protect item/data integrity without freezing entire environments or files. Agreed prerelease/new-save breaks may omit migration; do not invent speculative migration/recovery frameworks. Consult the human before introducing restrictive startup refusals, interaction restrictions or narrower compatibility. Explain concrete failures with relevant IDs/versions and an actionable next step.

## Select deeper checks by impact

- **Affected saved state:** Agree representative checks for changed block/entity state, stored ItemStacks or world data. Use `docs/persistence.md` when clean-process restart evidence is needed: seed/verify, save, clean stop, restart the same disposable world without reseeding, then assert restored fields. Reconnect and NBT roundtrips are additional evidence only. Keep both logs/transcript; missing probes, forced stops and never-run coverage remain explicit. Unrelated persistence is not a mandatory rerun.
- **Affected acquisition:** Review changed recipes, machines, drops, harvesting, worldgen, trades or hooks at the relevant scope. Select Atlas analysis when it answers an agreed question; its absence does not universally block ordinary Mod development. The repository-only `docs/survival.md` and packaged `templates/acquisition/README.md` cover exact Forge/Fabric 1.20.1 and NeoForge/Fabric 1.21.1 adapters. Inspect effective datapack resources, override provenance and execution semantics; add evidence-backed version-scoped definitions and positive/missing-prerequisite regressions only for the affected mechanisms. Unknown hooks and finite observations stay unknown/partial, never invented provider seeds or exhaustive absence/progression proof. Forge fluid runtime remains unverified.
- **Required current-build acquisition:** Configure `captureRuntime` using the survival guide. Deploy the current Run's actual distribution/dependencies/configs/datapacks, require fresh boot/session/generation and identity contract v1, and retain complete raw/companion evidence. An old dump cannot pass a required current-build check. Restart/recapture changed or unverifiable inputs; keep Atlas's independent bootstrap pin unchanged. Run the repository's `check:atlas`, `test:atlas` and `test:atlas:definitions` only when changing that integration, not for every Mod edit.

## Preserve harness safety

Runtime tests deploy recorded distribution JARs/dependencies, not arbitrary `build/libs` files. Keep worlds, settings and failed-run evidence. Never kill all Java processes or infer ownership from a stale PID.

Read `docs/storage.md` before opting into storage policies. Inventory with `mch storage --json`; `mch storage --clean --json` is a preview, and `--apply` needs authorization for its exact targets. Only managed dependencies with positively stopped owners and verified retained evidence qualify; historical unmarked data remains retained. With `after-suite`, keep reservations across restart gaps, lease each process phase, durably attach immutable scoped evidence to the saved report, release all leases and close the reservation after final use. Preserve previous `storageEvidence` references and use a 0.1.10-or-later reader. Clone/copy reuse supplies independent session files; logical inventory does not prove physical savings. These harness protections do not prescribe product startup or player interaction restrictions.
