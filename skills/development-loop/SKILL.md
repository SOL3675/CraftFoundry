---
name: development-loop
description: Build and validate a Minecraft mod through craft-foundry and inspect version-specific evidence after code changes.
---

Select a target with `mch targets --json`. Inspect its actual resolved classpath, source paths and mappings using `mch inspect --target <id> --json` before using Minecraft APIs. Prefer those sources when current documentation differs from the target version.

After implementing a change, run `mch build --target <id> --json`, followed by the affected `mch test --target <id> --suite <id> --json`. Runtime tests deploy the recorded distribution JAR and dependencies rather than arbitrary files in `build/libs`.

Use `mch report --run <run-id> --json` to inspect case statuses, detection counts, artifact hashes and failure evidence. Do not accept an exit code alone as proof of tests. Report unsupported, skipped, zero-detected and unstable retry results accurately. Before a release, execute `mch test --all --profile release --json` with every required suite.


When a change adds or alters crafting, a custom serializer/machine, drops, harvesting, world generation, trades or a Java acquisition hook, explicitly inspect the current Atlas capture and the affected item selection. For Fabric/NeoForge 1.21.1 or Forge/Fabric 1.20.1 use the repository-only `docs/survival.md` and `templates/acquisition/README.md`; an installed npm package alone does not supply the Atlas runner. Review whether a built-in normalizer covers the mechanism. Add/update a version-scoped, evidence-backed DefinitionPack and a `mechanisms` entry when custom semantics are needed, or retain an `unknown` reason for unverifiable hooks. Do not turn ingredient-consuming processes into provider/inventory seeds.

From the Atlas checkout, run `pnpm atlas datapack --snapshot <capture> --limit 100 --offset 0 --json` and page through the relevant resources. Use `pnpm atlas datapack yourmod:recipe/press.json --snapshot <capture> --json` and `pnpm atlas inspect yourmod:press --snapshot <capture> --json` to compare effective text/parsed data/byte SHA-256, source pack ID, visible low-to-high override stack and RecipeManager evidence. Record the capture session/generation and exact Mod version with your review. Review the effective variant; overridden files are evidence, not additional routes. Server captures are independent of JEI/EMI. For separate server JSON directories, configure the actual game JVM with `-Dcraftatlas.resourceDirectories=machines,yourmod/acquisition` before startup and make a fresh capture; directories are below `data/<namespace>/`, and `recipe` is always included on 1.21.1 and `recipes` on 1.20.1.

Raw presence is not semantic proof. Source-only, script-removed, unknown-serializer and unconfirmed resources need execution review, including conditions, power and custom APIs. A definition replacement must explicitly supply reviewed `execution: "executable"` as well as inputs, outputs, requirements and remaining unknowns; clearing unknowns alone cannot establish execution. Custom-directory resources need explicit additions, not guessed recipe IDs, and their unsupported interpretation coverage remains a blocker. Runtime-only entries require explicit execution review. Preserve raw provenance and field history; keep unresolved predicates, costs, hooks and incomplete coverage unknown. `captured: false` means an older snapshot lacks raw data, not that no datapack resources exist.

Add/update positive and missing-prerequisite regression cases (`without`), then run the affected survival process suite and inspect definition hashes, original/effective coverage, development diagnostics and detected case IDs in its evidence. Run `npm run check:atlas`, `npm run test:atlas` and `npm run test:atlas:definitions` in the Foundry repository when changing this integration. For a reviewed local Atlas commit not yet published/pinned, the latter accepts `-- --atlas-source <checkout>`. Unsupported serializers, absent mappings/tests, invalid definitions and incomplete acquisition coverage must remain explicit failures/unsupported; never guess arbitrary code semantics or claim a real-game pass from offline checks.

Use exact target resource paths: `yourmod:recipe/press.json` for 1.21.1, `yourmod:recipes/press.json` for 1.20.1. Keep Forge 1.20.1 Gradle/compile/game Java at 17/17/17, Fabric 1.20.1 at 21/17/17, and both 1.21.1 targets at 21/21/21. Inspect resolved APIs; do not reuse 1.21 codecs/components on 1.20 item/NBT/network serializers or broaden other versions.

Both 1.20.1 collectors support bounded loot/block/entity/world observations. Preserve completed manifests, matching session/generation, seeds, tool NBT, player/luck/damage context and chunk/height bounds. Command registration and finite-sample coverage are separate. Finite observations remain partial evidence, never exhaustive absence, sustainability or progression proof; they do not execute actual break/death events or prove arbitrary Java hooks. Preserve raw recipes/network hashes, viewer/world data, original/effective coverage and overlay history. JEI/EMI backing IDs, quantities and display entries do not prove execution or probability. Fabric 1.21.1 finite commands remain unsupported; Forge fluid runtime remains unverified. Validate a new Foundry packed consumer separately from prior Atlas game evidence using `docs/survival.md`; keep Atlas's independent Foundry pin unchanged.

Require `server-persistence` for supported Mods with persistent block entities/state, stored inventory or custom world data. Follow `docs/persistence.md`: seed and verify representative fields, flush/save, cleanly terminate the dedicated process, restart the same disposable world without reseeding, then assert restored values. Reconnect and NBT roundtrips are additional coverage only. Retain both launch logs and the persistence transcript; report missing probes, timeout/forced stop and never-run game coverage accurately.

For a required survival acquisition check, configure `captureRuntime` using `docs/survival.md#fresh-capture-and-built-jar-identity`. Deploy the current Run's distribution and all relevant dependency artifacts, prepare the actual configs/datapacks before launch, and let the runner issue a fresh boot nonce/request and freeze expected inputs before capture. Require collector/API identity contract v1 and inspect actual loaded origins, file/JVM identities, live session/generation, raw manifests and complete companion evidence. Old dumps remain readable for review but cannot pass a required current-build check; changed/missing/tampered/unverifiable identity requires restart/recapture or remains unsupported. Do not attach current hashes to an older dump or promote finite observations to exhaustive acquisition. Keep Atlas's independent bootstrap pin unchanged when testing a packed candidate overlay.
