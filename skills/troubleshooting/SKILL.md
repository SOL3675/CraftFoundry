---
name: troubleshooting
description: Diagnose Minecraft mod and craft-foundry failures from scoped reports, resolved APIs and actionable evidence while separating pending human checks.
---

Read `mch report --run <run-id> --json` and referenced evidence. Distinguish failed assertions from infrastructure errors, unsupported drivers, cancellation, timeouts and zero discovered tests. Record human-pending review separately: it is not a failure and does not justify exhaustive GUI automation. Before a fix, confirm AI checks, human checks and untested scope using the installed package's `templates/validation/README.md`; prior approval still covers routine steps within that plan.

Use [Minecraft development basics](../minecraft-development-basics/SKILL.md) when diagnosing item GUI desync/loss, wrong-side state, registration/resource failures or persistence. Check native menu/slot behavior and server ownership before inventing custom click handling. Resolve API names against the actual target sources/mappings. AI checks functionality, logic and essential affected state; detailed GUI interactions, feel and balance default to human checks.

For environment failures, use `mch doctor --json` and inspect Java roles, wrapper, display, configured hashes and EULA state. For API/build failures, inspect resolved dependencies/sources. For distribution failures, compare actual JAR identities and side placement; helper-free smoke and helper-driven checks establish different coverage. Give a concrete diagnostic with affected target/resource/Mod versions, relevant evidence and the next corrective action.

Treat normal Mod/config/datapack addition, update and removal as possible inputs to diagnose. Reproduce with relevant combinations around the affected integration rather than all Modpack combinations. Optional integrations should degrade locally. Unknown compatibility is not evidence of incompatibility. Consult the human before adding startup refusals, interaction restrictions or narrower runtime metadata. Keep build pins distinct from runtime ranges; NeoForge `loaderVersion` is its language-loader range. See `docs/development.md`.

Preserve the first failed attempt and matching source/dependency identities while needed for investigation, validation or review. Follow `docs/storage.md#evidence-retention-and-disposal`: obsolete evidence after an approved specification change and completed failed attempts no longer needed for current work may be deleted. A fix or passing rerun is not required just to permit disposal; failure alone does not require extra approval for authorized in-scope cleanup. Keep active/in-use data and explicitly retained evidence; ask if its purpose is unclear. Prefer deleting a whole unused Run, preserving every reference of any retained report. Deletion never establishes a pass. Approved specification changes may update obsolete validation requirements; do not remove requirements merely to hide failures.

A replay command cannot restore deleted evidence or dirty/untracked sources. Never kill all Java processes or trust a stale PID as ownership; investigate ambiguous build locks before removal. Protect item/data integrity without freezing an entire product environment. Respect agreed prerelease/new-save breaks and prefer a local native fix over a speculative migration/recovery framework.

For affected persistence, follow `docs/persistence.md`: inspect save/dirty hooks and restored representative fields, and use a clean-process `server-persistence` check when the approved question requires it. Reconnect and NBT roundtrips do not prove restart restoration. Preserve both logs/transcript; forced stop, missing probes and never-run coverage remain explicit. Do not retest every unrelated persistent subsystem.

For selected acquisition failures, use `templates/acquisition/README.md` and `docs/survival.md`. Inspect effective datapack byte hashes, pack/override provenance, RecipeManager/execution evidence, session/generation, conditions and custom hooks. Exact Forge/Fabric 1.20.1 and NeoForge/Fabric 1.21.1 adapters have different API/resource paths. Source-only/runtime-only entries, unknown serializers and incomplete/finite observations remain unknown/partial; never invent provider seeds or claim exhaustive absence/progression. Forge fluid runtime remains unverified. A required current-build `captureRuntime` check must have fresh identity and complete raw/companion evidence; old dumps remain review material only. Keep Atlas's independent bootstrap pin unchanged.

For disk pressure, read `docs/storage.md`, inventory with `mch storage --json` and preview with `mch storage --clean --json`. Apply only reviewed exact authorized targets; active/unknown-owner, incomplete or hash-mismatched units remain retained by dependency cleanup. Never alter metadata to bypass eligibility. The command retains historical caches and Run evidence; its `retain` disposition does not prohibit manual evidence disposal under the policy above. Protect worlds/settings still in use or separately needed. Deleting proof prevents dependent caches from qualifying for cleanup. Reclaimed dependencies need pinned downloads or valid local bytes; logical size/copy fallback does not prove physical saving.

For `after-suite`, check positive shutdown, immutable scoped evidence, durable `storageEvidence` attachment, all lease releases and final reservation closure. Reservations remain open across restart gaps. Use a 0.1.10-or-later reader and never strip evidence fields from retained reports. These are harness ownership/evidence protections, not product restrictions.
